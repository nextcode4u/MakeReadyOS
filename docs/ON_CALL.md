# Shared On-Call Workspace

Deployed to `mr-os.com` on 2026-09-14 as release `2c4b5a1`, including protected map uploads/markers, weekly rotation and swaps, the on-call calendar, AM/PM controls and the phone icon. Existing sharing settings were preserved. New instances still start with sharing disabled.

## Access Model

- Signed-in staff of every role can open the On-call module without a shared code. Managers and admins can manage it. API tokens cannot access its internal endpoints.
- This is one shared, instance-wide on-call group, independent of ordinary property memberships. People are contact records, not accounts. Covered properties are independent directory entries, not grants to other MakeReadyOS property records.
- `/on-call/` is a separate page without the main application navigation or login. It is read-only unless a coordinator unlocks the separate editing code. External sharing and external editing start disabled.
- When sharing is enabled, the schedule title/time zone, contact names/approved phone numbers, property names, shift times, backup assignments and shift notes are public. The editor labels these fields accordingly. Never put codes or private instructions in public fields.
- Addresses, shop locations, access codes, instructions and map/document links require the shared access code externally. Public API serialization explicitly excludes them before unlock. No private Wiki or Map records are copied automatically.
- Set a code of at least six characters before enabling sharing; prefer a longer passphrase. Copy share link copies only the URL. Share the code separately. Managers cannot retrieve the saved code; they can replace it.
- A separate signed, HttpOnly, SameSite-strict cookie grants eight hours of guide access and is scoped to `/api/on-call`. It never creates a regular application session. HTTPS deployments mark it Secure. Code rotation, sharing changes and Revoke all external guide sessions change a random access revision, invalidating earlier guest cookies.
- Unlock requires a trusted Origin. Persistent attempt buckets limit each IP to ten attempts per fifteen-minute window and the instance to 200. These limits count successful attempts too. They supplement, rather than replace, a strong shared passphrase and appropriate perimeter rate limiting.
- API responses are no-store and the service worker never caches on-call requests. The external page polls for updates/revocation, hides guides after session expiry, and clears displayed data when refresh fails. Previously viewed or copied information cannot be recalled; change actual property codes when necessary.

## Scheduling And Guides

### Separate External Editing Code

Managers/admins configure an optional editing passphrase in Manage on-call. It must be at least ten characters and different from the viewing code. It is hashed separately and excluded from exported workspace payloads. External coordinators open Coordinator editing access and unlock editing for one hour. This allows changes to the entire On-call workspace: schedules, rotation, contacts, covered properties, private guides, maps and markers. It does not authorize any other application module or changes to sharing settings, viewing/editing codes, or session revocation controls.

Editor cookies are signed, HttpOnly and SameSite-strict, with a separate revision from viewing cookies. Changing the editing code, disabling editing/sharing or revoking all sessions invalidates editor access. Lock editing & guides clears both cookies. Every write requires a trusted Origin and validates the editor session again inside the version-checked transaction. Map metadata cannot be forged; use the protected upload endpoint. Viewing-code sessions cannot write or upload. Both unlock endpoints share the persistent attempt limits. Changes are audited as shared-code editor actions, not attributed to a named staff member; use staff accounts when individual accountability is required. Private coordination reasons are available to editors but never to public/viewing-code readers.

Deploy migration `20260915130000_on_call_edit_access` before starting the new API. It adds a nullable editing hash and revision to existing workspaces without enabling editing or changing existing viewing codes. Native workspace backups exclude both access-code hashes; full database backups include them and must remain protected.

On-call displays and editors default to a 12-hour clock with explicit AM/PM controls, independent of browser clock preferences. The rail uses a phone icon with an On-call tooltip and accessible label. Stored handoff times remain 24-hour values for calculation (5:00 PM is stored as `17:00`).

Add contacts, then covered properties, then shifts. A shift selects a primary, an optional different backup and one or more properties. Dates are stored as UTC instants. Editors enter times in their device time zone; the schedule displays the configured IANA time zone. Copy to next week preserves device-local wall-clock times, including its daylight-saving rules; review copied times if the device and schedule zones differ.

The viewer shows current coverage, upcoming shifts, history and a property filter. End time is exclusive, allowing exact handoffs. Overlaps are allowed but flagged; absence of a recorded shift is explicitly a coverage gap, not proof that nobody is on duty. Contacts/properties referenced by saved shifts cannot be deleted without updating those shifts.

Automatic weekly rotation chooses a start date, handoff weekday/time, ordered contact list, and covered properties. The default is Friday at 5:00 PM, starting with the most recent handoff so the first person covers now. The first selected weekday on/after the configured date starts person one; every following week advances the list and wraps. Handoffs use the workspace time zone, not the server/device zone. Repeated DST times use the first occurrence; nonexistent times move forward by the DST gap. Normal 5:00 PM handoffs retain their local time.

Coverage is calculated from saved rules at read time, with a rolling year behind/ahead, so the system cannot exhaust a pre-generated batch or miss a rollover while offline. The open page switches its current-person display at the shift boundary, polls every minute for coordinator edits, and refreshes on focus. The on-call module has its own monthly calendar; this is not the unit make-ready calendar or an external calendar subscription. Both outgoing and incoming people appear on a handoff day; select the day for exact times.

Managers/admins can prepare a swap between two future saved rotation shifts, or add/edit/cancel a dated covering-person exception, including partial shifts and immediate emergency cover. The base order resumes after the exception. Reasons are staff-only even after an external guest unlocks guides. Exception times use the editor device zone, explicitly labeled; overlapping exceptions are rejected. Manual shifts take priority for their covered properties, so inspect them if a rotation exception does not change expected coverage. Rotation configuration changes recalculate projections, including the displayed historical window; use dated exceptions for one-off changes. This is not an immutable attendance ledger or an acknowledgement/notification system.

Uploaded maps can display shop and office pins in the protected viewer. Expand View map / shop & office, choose Mark shop or Mark office and tap the location; percentage fields provide a keyboard alternative. Save on-call persists markers. PDF page selection supports pages 1-50, with bounded server-side rasterization via Poppler; image maps use page 1. Replacing a map clears pins rather than applying old coordinates to a different drawing. Pins remain separate from the original download. Preview files are stored alongside uploads and require the same authorization as original downloads. See [Poppler's pdftoppm reference](https://skia.googlesource.com/third_party/poppler/+/master/utils/pdftoppm.1) for the converter's page selection and output-scaling options.

Guides support text instructions, shop/access codes, and optional HTTPS map/document links. Linked destinations need their own access controls; the module protects the link, not the destination. Links are not fetched by the server or embedded in the page and open with no referrer.

Managers/admins can upload one property map per covered property (PDF, PNG or JPEG, maximum 10 MB). Choose Edit property maps at the top of On-call to open the dedicated Property maps / mark shop & office section. Choosing a file saves pending on-call edits first; a failed save preserves the draft and prevents upload. Uploads save immediately; selecting another file replaces the current map. If saving succeeds but upload fails, the message explains that edits were saved. Save map markers and pending edits is available beside changed maps, or use Save on-call. Remove uploaded map takes effect on Save on-call. Failed or stale uploads leave the existing map intact. All signed-in staff can download; external downloads recheck the shared guide cookie, expiry, sharing switch and access revision on every request. File names/metadata are excluded from the locked public schedule. Downloads use no-store, nosniff and attachment headers; no publicly accessible storage URL is issued. Signature/type checks reject unsupported formats, but are not a malware scan. Upload trusted files only. Already downloaded copies cannot be revoked.

All edits are saved together with optimistic version checking. Errors preserve the draft; Reload saved workspace and closing a dirty editor require confirmation. Drafts and codes are intentionally not persisted in browser storage. Staff lose editing controls if their role changes.

## Backups And Limits

Database dumps include the workspace and access settings. Native JSON backups include directory/schedule content, including sensitive guides, but not the access-code hash or guest sessions. Protect those backup files. Native merge restore creates a missing workspace with sharing disabled and no code; an existing workspace is preserved rather than overwritten. Configure a new code and deliberately enable sharing after native restore.

Uploaded-map metadata is part of the workspace backup; file bytes live under `UPLOAD_DIR/on-call-maps` and require the paired uploads backup, not just a database/native JSON export. A missing file returns a recovery message rather than a broken public storage link. Replaced/removed files are no longer downloadable through the module but are retained on disk for backup consistency; automatic orphan cleanup is not implemented. Treat uploads and their backups as sensitive, including older maps.

Limits: 200 contacts, 100 properties, 2,000 manual shifts, 500 coverage exceptions and a 2 MB save request. No calendar subscription, notifications, external editing or per-guest identity is claimed. Shared-code users are not individually identifiable, and individual guest revocation is not supported.
